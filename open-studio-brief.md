# Open Studio — Project Brief

> A personal website that works as a museum in progress: a growing, browsable collection of the things I make and the things I'm curious about.

This brief is the starting context for a new repo. It describes what the project is, who it's for, how content is structured, and the main product decisions made so far. It is a spinoff of an earlier project (Momentum, a progress tracker). The idea it keeps from Momentum is *seeing things accumulate*. It drops the productivity-app framing, accounts, and logins.

---

## 1. Mission

I like tangibility: being able to see my work and interests build up over time and explore them. Two kinds of personal sites already exist, and neither fits:

- **Academic homepages** are focused and confident, but they're walls of text with no images and no personality beyond the work itself.
- **Portfolio sites** are visual and polished, but they take a long time to build and keep up, and they only show finished work.

Open Studio sits between them. It's a single place that shows:

- CS projects
- cooking experiments
- art and sketches
- books I've read
- things I've seen online that stuck with me

It should be easy to add to and organized enough to browse, without feeling like a raw dump. **The site itself is also meant to be a piece of work.** It should be visually considered, and it should quietly show that a computer scientist built it.

### Landing blurb (draft)

> Welcome to my open studio: a working collection of things I make and things I'm curious about. You'll find computer science, cooking experiments, art, and everything in between. Part portfolio, part sketchbook.
>
> I've never been great at showing the things I find meaningful, so this is partly an experiment in doing that, and partly a look at how I organize my own life. It's always in progress.
>
> If something here catches your eye, I'd love to talk about it. Send me a note.

## 2. Audiences

The same collection serves several kinds of visitors. Each one arrives through a different link:

| Visitor | Arrives from | Wants | Entry point |
|---|---|---|---|
| Friend / acquaintance | Social bio link | "What are you up to these days?" | Home: everything, newest first |
| Recruiter / professional | Resume, LinkedIn | Quick, credible picture of technical work | A **lens**, e.g. `/work` |
| Someone with a shared interest | A direct link to an entry or subject | Go deep on one topic | Subject or project page |
| Me | Phone / admin | Capture fast, curate later | Inbox + private views |

**Principle: one collection, many doors.** There's no separate site per audience. Every view is the same data with a filter or framing applied, and the filter state lives in the URL so every view can be shared.

## 3. Information architecture

### Layout: grid, not canvas

- The main browsing surface is a **grid of entry cards** (a masonry or uniform grid that works well with images).
- An open, free-form canvas or "map" layout is **out of scope**. It's too messy and hard to scan.

### Drill-down hierarchy with breadcrumbs

Content is organized in a three-level funnel:

```
Subject  →  Project  →  Session
e.g. Computer Science → Open Studio (this site) → "Built capture endpoint, Oct 3"
     Kitchen          → Sourdough              → "Bake #4, higher hydration"
     Studio           → Figure drawing         → "Life drawing, Oct 1"
     Library          → (no project)           → —
```

- **Subject**: a small, stable, curated set (roughly 4–8). These are the "rooms" of the museum.
- **Project**: an ongoing body of work or a focused interest within a subject.
- **Session**: one sitting or one event within a project. It's optional.
- Every entry belongs to a subject. Project and session are optional, because loose captures and one-off interests won't have them.
- Browsing goes Home → Subject grid → Project grid → Session (or entry), with **breadcrumbs** at every level (`Home / Kitchen / Sourdough / Bake #4`).

### Tags: a second, cross-cutting axis

- The hierarchy answers *where something lives*. Tags answer *what it connects to*.
- Tags are **generated by AI on submission** and can be edited afterward.
- On any grid you can narrow the results with tag filter chips. Filters combine with the hierarchy (e.g. `/kitchen?tag=fermentation`).
- When a filter is applied, entries can be visually de-emphasized instead of hidden. Crossovers between subjects (e.g. a CS entry that's also tagged cooking) are a feature and should stay visible.

### Lenses (curated entry points)

A **lens** is a saved view for a specific audience. It has:

- an intro line
- a filter (by subject and/or tags)
- a few pinned items at the top
- a sort order

Start with one or two lenses (e.g. `/work`) and add more only when there's a real need.

### Related work

- Each entry page shows **"Related"** entries found by embedding similarity. These deliberately include entries *outside* the current project or subject, to surface unexpected connections.
- Each entry page also shows **manual links**: connections I made on purpose to other entries.

## 4. Data model (first draft)

### Entry (the core unit; also called an "artifact")

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | |
| `title` | text | Can be auto-filled from link metadata |
| `description` | text | My explanation of what this is and **why it's here**. The most important field. |
| `kind` | enum | Medium/type: `link`, `note`, `book`, `artwork`, `sketch`, `project_log`, `recipe`, `video`, `post`, … (extensible) |
| `occurred_at` | timestamptz | When it happened or when I experienced it. Supports backfilling old work. |
| `created_at` | timestamptz | Upload time (system-set) |
| `updated_at` | timestamptz | |
| `author_type` | enum | `self` \| `external` |
| `source` | object, nullable | For external content: `{ name, url, platform }` (e.g. an X post, an Instagram reel, a book's author). Can be blank. |
| `media` | list | Images, screenshots, attachments. A screenshot is the fallback for sources that are hard to scrape (Instagram, X). |
| `link_preview` | object, nullable | Unfurled OpenGraph/oEmbed data: title, image, site name |
| `subject_id` | fk | Required |
| `project_id` | fk, nullable | |
| `session_id` | fk, nullable | |
| `tags` | list | Each tag has `{ name, origin: "ai" \| "manual" }` |
| `embedding` | vector | Plus `embedding_model` and `embedded_at`. Regenerated when the content changes. |
| `visibility` | enum | `private` \| `unlisted` \| `public` |
| `status` | enum | `inbox` (captured, not yet annotated) \| `published` |
| `featured` | bool | Shows up prominently and is pinnable in lenses |

### Supporting tables

- **Subject**: `id, slug, name, description, sort_order, cover_image`
- **Project**: `id, subject_id, slug, name, description, status (active/paused/archived), started_at, cover_image, visibility`
- **Session**: `id, project_id, title, occurred_at, notes`
- **EntryLink** (manual links): `from_entry_id, to_entry_id, note`
- **Lens**: `slug, title, intro, filter (subjects/tags), pinned_entry_ids, sort`

### Open modeling questions

- Should a session be its own table, or just a grouping label/date within a project? Starting with a table is simplest if sessions need their own page.
- Should tags be free text or a managed vocabulary? AI suggestions should prefer tags that already exist so they don't splinter.
- What text goes into the embedding? Probably title + description + tags + any extracted text or link-preview text.

## 5. Capture flow

Adding an entry should take seconds. Curating it can happen later.

1. **Capture.** I share a URL (or a photo or text) from my phone's share sheet → it goes to a capture endpoint.
   - The first version can be an iOS Shortcut that POSTs to an authenticated API. A native app or PWA share target comes later.
2. **Enrich (automatic).** The server:
   - unfurls the link (OpenGraph/oEmbed)
   - stores media
   - suggests a title, kind, subject/project and tags (via an LLM)
   - computes an embedding
3. **Inbox.** The entry lands as `status: inbox`, `visibility: private`.
4. **Annotate.** I add the "why it's here" description, adjust the tags and placement, set visibility, and publish.
   - Annotating can happen right away or in batches later.
5. **Curated entries** (book write-ups, project write-ups, art pieces) use the same model. They're written directly in an admin editor and get richer descriptions and more media.

**Single-owner app:** only I can write. Visitors are read-only and see only `public` content, plus `unlisted` content if they have the direct link. No user accounts are needed beyond owner auth for the admin and capture API.

## 6. Design direction

- **Text-first, image-rich.** Strong typography, generous whitespace, very little visual decoration. The images inside entries supply the color and texture.
- **Museum wall labels.** Every card and entry shows a consistent placard: *title · kind · date · source*, plus the "why it's here" line. This consistency is what keeps a mixed collection from looking like a hodgepodge.
- **"In progress" is part of the design.** Recently added items and active projects are visible, and the site should feel alive and growing.
- **Quiet CS signals:**
  - clean, readable URLs (`/kitchen/sourdough`)
  - an RSS feed
  - a colophon page explaining how the site is built
  - maybe a small activity strip or a live entry count
  - fast and accessible
- Works well on mobile, since bio links will mostly be opened on phones.

---

## 7. Non-goals (for now)

- A free-form canvas or map layout
- Multi-user accounts, social features, comments
- A native mobile app (start with a Shortcut or PWA)
- Fully automatic publishing. AI suggests; I decide what goes public.

---

## 8. Suggested build phases

1. **Foundation:**
   - data model + database (with vector support, e.g. Postgres + pgvector)
   - admin CRUD for entries, subjects and projects
   - public grid + entry page
2. **Browsing:**
   - subject → project → session drill-down with breadcrumbs
   - tag filters stored in URL state
   - visibility rules
3. **Capture:**
   - authenticated capture API + iOS Shortcut
   - link unfurling
   - inbox view
4. **Intelligence:**
   - AI tag/subject suggestions
   - embeddings + "Related" section
   - manual entry links
5. **Framing:**
   - landing page with the blurb
   - lenses (`/work`)
   - RSS feed, colophon
   - visual polish

## 9. Decisions still open

- Tech stack and hosting (needs a database with vector search, image storage, and an LLM + embedding provider)
- Final list of subjects
- Whether to show maturity markers (seedling → evergreen) on entries
- How much of the Momentum-style "accumulation" view (activity graph, counts) to bring over
